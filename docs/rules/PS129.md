# PS129 · server-setting-change

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`ALTER SYSTEM`, `ALTER DATABASE ... SET` and `ALTER ROLE ... SET` (including `RESET`).

## Why it matters

`SET` and `SET LOCAL` only affect the migration's own session. These statements persist a setting for the whole server, every new session of a database, or every new session of a role, so a change made for the migration (a longer `statement_timeout`, a larger `work_mem`) silently applies to application connections opened afterwards. `ALTER SYSTEM` cannot run in a transaction block, is not undone if the migration fails later, and only takes effect on a reload or restart, which separates the effect from the deploy that caused it.

## Example

Flagged:

```sql
ALTER ROLE migrator SET statement_timeout = 0;
UPDATE accounts SET plan = 'basic' WHERE plan IS NULL AND id < 50000;
```

Preferred:

```sql
SET statement_timeout = '15min';
UPDATE accounts SET plan = 'basic' WHERE plan IS NULL AND id < 50000;
```

## How ProdShadow verifies it

Static only: the disposable server is discarded after each phase, so the candidate run cannot show the lasting effect.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS129: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS129 reason="why this is acceptable" expires=2027-06-30
```
