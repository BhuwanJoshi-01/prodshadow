# OBS002 · migration-lock-timeout

| Default severity | Evidence |
|---|---|
| critical | observed |

## What it detects

The migration failed with SQLSTATE `55P03` (`lock_not_available`): it could not acquire its lock within `migration.lock_timeout_ms`. The message names the sessions it waited for, by application name.

## Why it matters

In production, without a `lock_timeout`, the statement would have kept waiting — and every query on the table would have queued behind it. This is the lock-queue outage pattern behind most public migration postmortems.

## Example

Flagged:

```sql
ALTER TABLE invoices ADD COLUMN external_reference text;  -- while a report holds a transaction open
```

Preferred:

```sql
SET lock_timeout = '2s';
ALTER TABLE invoices ADD COLUMN external_reference text;
-- deploy outside reporting windows and retry on 55P03 with backoff
```

## How ProdShadow verifies it

Model the long transaction as a background session (`hold_ms`). See [examples/long-running-transaction](../../examples/long-running-transaction).

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS002: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore OBS002 reason="why this is acceptable" expires=2027-06-30
```
