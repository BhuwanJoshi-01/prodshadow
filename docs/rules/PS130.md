# PS130 · sequence-reset

| Default severity | Evidence |
|---|---|
| warning | heuristic |

## What it detects

`ALTER SEQUENCE ... RESTART`, `setval()` with a constant value, and `TRUNCATE ... RESTART IDENTITY`, on sequences that existed before the migration. `setval()` with a value computed from the data, such as `(SELECT max(id) FROM orders)`, is not flagged.

## Why it matters

A sequence moved to a fixed value hands out that value next. If production already has rows with higher ids, which a development database usually does not, every insert that relies on the sequence fails with a duplicate key error until the sequence passes the existing ids. The finding is a heuristic because the migration cannot show which ids exist.

## Example

Flagged:

```sql
SELECT setval('orders_id_seq', 1000);
```

Preferred:

```sql
SELECT setval('orders_id_seq', (SELECT coalesce(max(id), 0) + 1 FROM orders), false);
```

## How ProdShadow verifies it

The candidate run uses the fixture's data, which may not contain the ids that collide in production.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS130: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS130 reason="why this is acceptable" expires=2027-06-30
```
