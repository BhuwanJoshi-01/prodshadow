# PS160 · view-replace-incompatible

| Default severity | Evidence |
|---|---|
| critical | static |

## What it detects

`CREATE OR REPLACE VIEW` whose select list, compared with the existing view from the fixture schema (or an earlier statement), drops a column, or has a different column name at an existing position. Column names are derived as PostgreSQL does: the alias, the column, the function name. Without a fixture schema the rule is silent; confidence is medium because data types are not compared.

## Why it matters

`CREATE OR REPLACE VIEW` only accepts a definition that keeps every existing column with the same name, type and position, and adds new columns at the end. Anything else fails with SQLSTATE `42P16` (`cannot drop columns from view`, `cannot change name of view column`). Removing a column from a view is a common clean-up step, and in a file that is not one transaction the statements before it stay applied.

## Example

Flagged:

```sql
-- recent_orders was SELECT id, status FROM orders
CREATE OR REPLACE VIEW recent_orders AS SELECT id FROM orders;
```

Preferred:

```sql
BEGIN;
DROP VIEW recent_orders;
CREATE VIEW recent_orders AS SELECT id FROM orders;
COMMIT;
```

## How ProdShadow verifies it

The failure oracle integration test runs a dropping and a reordering replacement against PostgreSQL and checks the SQLSTATE; `verify` reports the failure as `OBS003`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS160: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS160 reason="why this is acceptable" expires=2027-06-30
```
