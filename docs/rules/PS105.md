# PS105 · alter-column-type

| Default severity | Evidence |
|---|---|
| warning | heuristic |

## What it detects

`ALTER TABLE ... ALTER COLUMN ... TYPE` on a pre-existing table.

## Why it matters

Changing a column's type usually rewrites the table and rebuilds every index that includes the column, all under `ACCESS EXCLUSIVE`. Some conversions are binary-compatible and skip the rewrite (for example `varchar(n)` to `text` or to a wider `varchar`), which is why the finding usually carries medium or low confidence: the current type is not visible in the migration.

Confidence is adjusted from what the statement does show:

| Statement | Confidence |
|---|---|
| A `USING` expression other than the bare column, e.g. `USING ref::integer` | high: every row is converted |
| Target `text`, `varchar`, `numeric` or `cidr` without a limit | low: often binary-compatible |
| Target `varchar(n)`, `numeric(p, s)` or `varbit(n)` | low: raising a limit avoids the rewrite, lowering it does not |
| Anything else | medium |

## Example

Flagged:

```sql
ALTER TABLE orders ALTER COLUMN amount TYPE bigint;
```

Preferred:

```sql
ALTER TABLE orders ADD COLUMN amount_v2 bigint;
-- dual-write from the application, backfill in batches,
-- switch readers, then drop the old column in a later release
```

## How ProdShadow verifies it

The experiment shows whether the conversion rewrote the table on your fixture (the migration's duration and WAL volume grow with table size) and how long traffic waited.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS105: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS105 reason="why this is acceptable" expires=2027-06-30
```
