# PS111 · unbounded-dml

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`UPDATE` or `DELETE` without a `WHERE` clause on a pre-existing table.

## Why it matters

Every row is locked until the statement's transaction commits, so concurrent writes to any row wait for the whole backfill. The change also produces WAL and dead tuples for the entire table in one transaction.

## Example

Flagged:

```sql
UPDATE subscribers SET email_normalized = lower(email);
```

Preferred:

```sql
-- run repeatedly from a script, committing each batch
UPDATE subscribers SET email_normalized = lower(email)
WHERE id BETWEEN $1 AND $2 AND email_normalized IS NULL;
```

## How ProdShadow verifies it

Write scenarios queue on the backfill's transaction; the phase counters show the WAL volume. See [examples/backfill-heavy](../../examples/backfill-heavy).

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS111: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS111 reason="why this is acceptable" expires=2027-06-30
```
