# PS157 · referenced-table-removed

| Default severity | Evidence |
|---|---|
| critical | static |

## What it detects

`DROP TABLE` or `TRUNCATE` without `CASCADE` on a table that foreign keys of other tables still reference at that point of the migration. Foreign keys are learned from the fixture schema (`fixture.schema`) and from earlier statements of the migration, including ones that drop them; without a schema the rule is silent.

## Why it matters

PostgreSQL refuses both statements while another table's foreign key points at the table (`cannot drop table ... because other objects depend on it`, `cannot truncate a table referenced in a foreign key constraint`), even when the referencing table is empty. The deploy fails at this statement, and in a file that is not one transaction the statements before it stay applied (see [PS155](PS155.md)).

## Example

Flagged:

```sql
-- invoices.customer_id REFERENCES customers
DROP TABLE customers;
```

Preferred:

```sql
ALTER TABLE invoices DROP CONSTRAINT invoices_customer_id_fkey;
DROP TABLE customers;
-- or truncate the referencing tables in the same statement:
TRUNCATE customers, invoices;
```

## How ProdShadow verifies it

`verify` runs the migration and reports the failure as `OBS003` with SQLSTATE `2BP01` or `0A000`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS157: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS157 reason="why this is acceptable" expires=2027-06-30
```
