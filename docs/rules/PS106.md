# PS106 · set-not-null-scans-table

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`ALTER TABLE ... ALTER COLUMN ... SET NOT NULL`, unless an earlier transaction of the same migration left a validated `CHECK (col IS NOT NULL)` on that column (added without `NOT VALID`, or added `NOT VALID` and then validated). A constraint created by an earlier migration is not visible, so the rule may still report a statement that skips the scan in production.

## Why it matters

PostgreSQL scans the whole table to verify that no row is `NULL`, while holding `ACCESS EXCLUSIVE`. Since PostgreSQL 12 the scan is skipped if a validated `CHECK (col IS NOT NULL)` constraint already exists, and that constraint can be validated with a much weaker lock.

## Example

Flagged:

```sql
ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
```

Preferred:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_status_not_null CHECK (status IS NOT NULL) NOT VALID;
-- separate transaction; takes SHARE UPDATE EXCLUSIVE only
ALTER TABLE orders VALIDATE CONSTRAINT orders_status_not_null;
ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
ALTER TABLE orders DROP CONSTRAINT orders_status_not_null;
```

## How ProdShadow verifies it

The candidate run measures how long the scan held the lock on your fixture.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS106: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS106 reason="why this is acceptable" expires=2027-06-30
```
