# PS117 · procedural-code

| Default severity | Evidence |
|---|---|
| info | experiment quality |

## What it detects

`CALL` of a procedure that the fixture schema does not define (or that uses dynamic SQL), `DO` blocks in languages other than PL/pgSQL, and PL/pgSQL `DO` blocks that run dynamic SQL (`EXECUTE`). The static SQL of a PL/pgSQL `DO` block (its statements, `PERFORM`, and the queries in conditions and assignments) is analysed like any other statement, so a block without dynamic SQL is not reported and its locks are listed.

## Why it matters

Dynamic SQL and procedures can run any statement, so their locks cannot be predicted from the SQL text. Only the experiment shows what they do.

## Example

Flagged:

```sql
DO $$ BEGIN EXECUTE 'ALTER TABLE ' || 'orders' || ' ADD COLUMN x int'; END $$;
```

Preferred:

```sql
-- prefer plain SQL migrations where possible
ALTER TABLE orders ADD COLUMN x int;
```

## How ProdShadow verifies it

The candidate run measures the procedure's real effect on the workload.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS117: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS117 reason="why this is acceptable" expires=2027-06-30
```
