# PS101 · create-index-blocks-writes

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`CREATE INDEX` (or `CREATE UNIQUE INDEX`) without `CONCURRENTLY` on a table that existed before the migration.

## Why it matters

A plain index build takes a `SHARE` lock on the table for the entire build. `SHARE` conflicts with `ROW EXCLUSIVE`, so every `INSERT`, `UPDATE` and `DELETE` on the table waits until the index is complete. Reads continue. On a large table the build can take minutes or hours.

## Example

Flagged:

```sql
CREATE INDEX orders_status_idx ON orders (status);
```

Preferred:

```sql
-- in its own migration step, outside BEGIN/COMMIT
CREATE INDEX CONCURRENTLY orders_status_idx ON orders (status);
```

## How ProdShadow verifies it

The experiment shows the stall directly: write scenarios stop while reads continue, and `OBS001` reports the longest wait against `policy.max_lock_wait_ms`. See [examples/blocking-index](../../examples/blocking-index).

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS101: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS101 reason="why this is acceptable" expires=2027-06-30
```
