# PS153 · table-without-primary-key

| Default severity | Evidence |
|---|---|
| info | static |

## What it detects

`CREATE TABLE` (not temporary) without a primary key, when no later statement of the migration adds one. Partitions, which inherit the parent's key, and tables created with `LIKE`, which may copy one, are not reported.

## Why it matters

Without a primary key, rows cannot be identified reliably. Logical replication and change data capture cannot replicate updates and deletes of the table unless it uses `REPLICA IDENTITY FULL`, which logs whole rows (see [PS147](PS147.md)), and once the table is in a publication, updates and deletes on it fail. ORMs, online schema change tools and data sync tools often require a key. Append-only logs sometimes do without one, which is why this is information.

## Example

Flagged:

```sql
CREATE TABLE audit_log (
  at timestamptz NOT NULL,
  payload jsonb NOT NULL
);
```

Preferred:

```sql
CREATE TABLE audit_log (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  at timestamptz NOT NULL,
  payload jsonb NOT NULL
);
```

## How ProdShadow verifies it

Static only.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS153: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS153 reason="why this is acceptable" expires=2027-06-30
```
