# PS112 · explicit-table-lock

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`LOCK TABLE` in a mode that blocks writes (`SHARE` and stronger) or reads (`ACCESS EXCLUSIVE`, the default mode).

## Why it matters

The lock is held until the transaction ends. Every statement in that transaction extends the outage, and without `lock_timeout` the `LOCK` itself can queue behind a long transaction while blocking everything behind it.

## Example

Flagged:

```sql
BEGIN;
LOCK TABLE orders;
UPDATE orders SET status = 'archived' WHERE created_at < '2024-01-01';
COMMIT;
```

Preferred:

```sql
SET lock_timeout = '2s';
BEGIN;
LOCK TABLE orders IN SHARE ROW EXCLUSIVE MODE;  -- the weakest mode that is enough
-- keep the transaction short
COMMIT;
```

## How ProdShadow verifies it

The candidate run shows how long sessions waited behind the explicit lock.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS112: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS112 reason="why this is acceptable" expires=2027-06-30
```
