# OBS013 · app-version-incompatible

| Default severity | Evidence |
|---|---|
| critical | observed |

## What it detects

A compatibility probe that worked on the schema before the migration failed after it, in a candidate phase. Probes are the queries an application version still depends on, declared per version in the workload's `compatibility` section. One finding is reported per broken version, listing its failing probes with SQLSTATE and message.

## Why it matters

During a rolling deploy, and for as long as old instances, workers or cron jobs keep running, the previous application version runs against the new schema. A dropped or renamed column, a new `NOT NULL` column without a default, or a changed type breaks that version's queries even though the new version works. Unlike the scenario mix, probes check every query a version depends on once, so rarely used queries are covered too.

## Example

Flagged:

```sql
compatibility:
  - version: "2026.10"   # still deployed
    probes:
      - id: product_by_sku
        sql: "SELECT id, legacy_sku FROM products WHERE id = $1"
        parameters: [{generator: int_range, min: 1, max: 100}]
# migration: ALTER TABLE products DROP COLUMN legacy_sku;
```

Preferred:

```sql
# release 2026.11 stops reading legacy_sku; once no 2026.10 instance runs,
# remove that version from compatibility and drop the column.
```

## How ProdShadow verifies it

Each probe runs as the application role, before the workload starts and after the migration finishes, in every candidate phase, inside a transaction that is rolled back. Confidence reflects how many candidate repeats the probe broke in.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS013: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore OBS013 reason="why this is acceptable" expires=2027-06-30
```
