# PS161 · concurrent-detach-with-default

| Default severity | Evidence |
|---|---|
| critical | static |

## What it detects

`ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY` on a partitioned table that, according to the fixture schema and the migration so far, has a `DEFAULT` partition. Without a fixture schema the rule is silent.

## Why it matters

Detaching concurrently is the usual fix for the `ACCESS EXCLUSIVE` lock a plain `DETACH PARTITION` takes on the parent ([PS140](PS140.md)), but PostgreSQL refuses it while a default partition exists (SQLSTATE `55000`): the default partition's implicit range would change under concurrent inserts. The migration fails at this statement. A plain detach, attach or new partition also locks the default partition with `ACCESS EXCLUSIVE` and checks its rows, which `plan` and `inspect` list as `via default partition of ...`.

## Example

Flagged:

```sql
-- events has a DEFAULT partition events_other
ALTER TABLE events DETACH PARTITION events_2024 CONCURRENTLY;
```

Preferred:

```sql
SET lock_timeout = '2s';
ALTER TABLE events DETACH PARTITION events_2024;
-- retried by the deploy tool on lock_timeout (migration.lock_retries)
```

## How ProdShadow verifies it

The failure oracle integration test runs the statement against PostgreSQL and checks the SQLSTATE; the lock oracle checks the default partition locks.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS161: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS161 reason="why this is acceptable" expires=2027-06-30
```
