# PS133 · foreign-key-without-index

| Default severity | Evidence |
|---|---|
| info | heuristic |

## What it detects

A foreign key added by `CREATE TABLE` or `ALTER TABLE` whose referencing columns are not the leading columns of any index, primary key or unique constraint the migration creates on that table (in any order).

## Why it matters

PostgreSQL indexes the referenced side of a foreign key (it must be a primary key or unique) but not the referencing side. Without an index there, every `DELETE` of a referenced row, and every update of its key, scans the referencing table to find dependent rows, holding row locks while it does; `ON DELETE CASCADE` does the same. On large tables this turns a single-row delete into a sequential scan. For a table created in the migration the index cannot exist yet; for an existing table it may, which ProdShadow cannot see, so confidence is low there.

## Example

Flagged:

```sql
CREATE TABLE refunds (
  id bigint PRIMARY KEY,
  order_id bigint NOT NULL REFERENCES orders (id)
);
```

Preferred:

```sql
CREATE TABLE refunds (
  id bigint PRIMARY KEY,
  order_id bigint NOT NULL REFERENCES orders (id)
);
CREATE INDEX refunds_order_id_idx ON refunds (order_id);
```

## How ProdShadow verifies it

Static only. Workload scenarios that delete from the referenced table show the cost as latency in the candidate run once the fixture has enough rows.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS133: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS133 reason="why this is acceptable" expires=2027-06-30
```
