# PS135 · statement-timeout-disabled

| Default severity | Evidence |
|---|---|
| info | static |

## What it detects

`SET statement_timeout = 0` (or `SET LOCAL`), in any unit.

## Why it matters

Many deploy tools set a `statement_timeout` so that a migration that runs far longer than expected is cancelled instead of holding its locks indefinitely. Setting it to 0 removes that limit for every following statement of the session. It is sometimes deliberate for a long, non-blocking backfill, so the rule only informs; a finite limit for the statements that need it keeps the safety net.

## Example

Flagged:

```sql
SET statement_timeout = 0;
UPDATE accounts SET plan = 'basic' WHERE plan IS NULL;
```

Preferred:

```sql
BEGIN;
SET LOCAL statement_timeout = '15min';
UPDATE accounts SET plan = 'basic' WHERE plan IS NULL;
COMMIT;
```

## How ProdShadow verifies it

The candidate run applies `migration.statement_timeout_ms` before the migration's own statements, so a `SET statement_timeout = 0` in the migration overrides it there too; OBS009 still reports a long migration if `policy.max_migration_seconds` is set.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS135: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS135 reason="why this is acceptable" expires=2027-06-30
```
