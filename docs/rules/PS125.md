# PS125 · integrity-checks-disabled

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`SET session_replication_role = replica` and `ALTER TABLE ... DISABLE TRIGGER ALL` on a table that existed before the migration.

## Why it matters

PostgreSQL enforces foreign keys with internal triggers. Setting `session_replication_role` to `replica` turns off all ordinary triggers for the session (or transaction, with `SET LOCAL`), and `DISABLE TRIGGER ALL` turns off a table's triggers including the internal ones. Rows written meanwhile are never checked: the constraint stays marked valid, so a later `VALIDATE CONSTRAINT` does nothing, and orphaned rows surface later as application errors. `DISABLE TRIGGER USER` and disabling a trigger by name leave foreign keys enforced and are not flagged.

## Example

Flagged:

```sql
SET session_replication_role = replica;
INSERT INTO line_items SELECT * FROM import_line_items;
```

Preferred:

```sql
ALTER TABLE line_items DROP CONSTRAINT line_items_order_fk;
INSERT INTO line_items SELECT * FROM import_line_items;
ALTER TABLE line_items ADD CONSTRAINT line_items_order_fk
  FOREIGN KEY (order_id) REFERENCES orders (id) NOT VALID;
ALTER TABLE line_items VALIDATE CONSTRAINT line_items_order_fk;
```

## How ProdShadow verifies it

Static only: the candidate run does not look for rows that violate a foreign key.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS125: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS125 reason="why this is acceptable" expires=2027-06-30
```
