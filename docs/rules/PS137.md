# PS137 · constraint-left-not-valid

| Default severity | Evidence |
|---|---|
| info | static |

## What it detects

`ALTER TABLE ... ADD CONSTRAINT ... NOT VALID` with no `VALIDATE CONSTRAINT` for that constraint later in the migration.

## Why it matters

A `NOT VALID` constraint is enforced for rows inserted or updated from now on, but existing rows are not checked until `VALIDATE CONSTRAINT` runs. Until then the constraint does not prove anything about old data: a `NOT VALID` `CHECK (col IS NOT NULL)` cannot let `SET NOT NULL` skip its table scan, and the planner cannot rely on it. Validating in the next migration is the recommended pattern, so this is a reminder, not a warning.

## Example

Flagged:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_total_positive
  CHECK (total >= 0) NOT VALID;
-- and no later VALIDATE CONSTRAINT
```

Preferred:

```sql
-- this migration
ALTER TABLE orders ADD CONSTRAINT orders_total_positive
  CHECK (total >= 0) NOT VALID;

-- next migration
ALTER TABLE orders VALIDATE CONSTRAINT orders_total_positive;
```

## How ProdShadow verifies it

Static only. Check for constraints that were never validated with `SELECT conrelid::regclass, conname FROM pg_constraint WHERE NOT convalidated;`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS137: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS137 reason="why this is acceptable" expires=2027-06-30
```
