# PS119 · foreign-key-locks-referenced-table

| Default severity | Evidence |
|---|---|
| info | static |

## What it detects

`CREATE TABLE` with a foreign key that references a pre-existing table.

## Why it matters

Creating the foreign key takes `SHARE ROW EXCLUSIVE` on the referenced table, which waits for and then blocks writes to it. The new table is empty, so the lock is brief, but it still queues behind long transactions on the referenced table.

## Example

Flagged:

```sql
CREATE TABLE refunds (id bigint PRIMARY KEY, order_id bigint REFERENCES orders (id));
```

Preferred:

```sql
SET lock_timeout = '2s';
CREATE TABLE refunds (id bigint PRIMARY KEY, order_id bigint REFERENCES orders (id));
```

## How ProdShadow verifies it

With a background session on the referenced table, the candidate run shows the queue.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS119: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS119 reason="why this is acceptable" expires=2027-06-30
```
