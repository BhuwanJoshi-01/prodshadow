# PS143 · unlogged-table

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`CREATE UNLOGGED TABLE` (including `CREATE UNLOGGED TABLE ... AS`) and `ALTER TABLE ... SET UNLOGGED`. Temporary tables are not reported.

## Why it matters

Writes to an unlogged table skip the write-ahead log. That makes them faster, but after a crash or an unclean shutdown PostgreSQL truncates the table, physical standbys and WAL-based backups never contain its rows, and after a failover it is empty. `SET UNLOGGED` on an existing table also rewrites it under `ACCESS EXCLUSIVE` ([PS113](PS113.md)). Unlogged tables suit scratch data that can be rebuilt, not data the application relies on.

## Example

Flagged:

```sql
ALTER TABLE events SET UNLOGGED;
```

Preferred:

```sql
-- scratch data for a one-off load, dropped afterwards
CREATE UNLOGGED TABLE import_rows (id bigint, payload jsonb);
-- ... load and merge into events ...
DROP TABLE import_rows;
```

## How ProdShadow verifies it

Static only: the disposable server does not crash or fail over during the run.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS143: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS143 reason="why this is acceptable" expires=2027-06-30
```
