# PS149 · expired-annotation

| Default severity | Evidence |
|---|---|
| info | static |

## What it detects

A valid `-- prodshadow:ignore` directive whose `expires` date has passed. The directive no longer suppresses anything.

## Why it matters

Expiry dates make suppressions get reviewed again. When one passes, the findings it suppressed reappear, often in an unrelated pull request. This rule explains why, names the rules and the original reason, and points at the comment to renew or remove. Suppression files report expired entries in the decision; this is the inline equivalent.

## Example

Flagged:

```sql
-- prodshadow:ignore PS101 reason="lookup table with 40 rows" expires=2026-01-31
CREATE INDEX countries_name_idx ON countries (name);
```

Preferred:

```sql
-- reviewed again: still 40 rows
-- prodshadow:ignore PS101 reason="lookup table with 40 rows" expires=2027-01-31
CREATE INDEX countries_name_idx ON countries (name);
```

## How ProdShadow verifies it

Static only.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS149: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS149 reason="why this is acceptable" expires=2027-06-30
```
