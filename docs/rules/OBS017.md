# OBS017 · stall-without-lock-conflict

| Default severity | Evidence |
|---|---|
| info | observed |

## What it detects

A scenario stalled beyond its baseline p99 while the migration ran, by more than `policy.max_lock_wait_ms` (500 ms when no budget is set), although none of the table locks its SQL takes conflicts with a lock of the migration. The prediction uses the lock conflict matrix and the fixture schema, as `plan` does (`predicted_conflicts` in the report).

## Why it matters

Table locks explain most migration stalls, and a stall they do not explain points at something else worth knowing. The usual cause is row locks: an `UPDATE` or `DELETE` in the migration locks every row it changes until it commits, and application updates of the same rows wait, although `ROW EXCLUSIVE` does not conflict with `ROW EXCLUSIVE`. Other causes are a foreign key, partition or trigger that production has but the fixture schema lacks, so the prediction missed a lock, and contention for I/O and CPU while the migration rewrites data.

## Example

Flagged:

```sql
-- updates every row in one transaction; concurrent updates of any row wait
UPDATE accounts SET balance_cents = balance * 100;
```

Preferred:

```sql
-- in batches, each committed on its own
UPDATE accounts SET balance_cents = balance * 100
WHERE id BETWEEN 1 AND 10000;
```

## How ProdShadow verifies it

Compare *Predicted conflict* and *Max during migration* in the scenario comparison. The [backfill-heavy example](../../examples/backfill-heavy) shows row-lock waits.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS017: critical   # or info, warning, off
```

Suppress a reviewed case in the suppressions file (`policy.suppressions`):

```yaml
version: 1
suppressions:
  - rule: OBS017
    reason: "why this is acceptable"
    expires: 2027-06-30
```
