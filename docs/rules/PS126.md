# PS126 · database-wide-maintenance

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`VACUUM` or `ANALYZE` without a table list, and `REINDEX DATABASE`, `REINDEX SYSTEM` or `REINDEX SCHEMA`.

## Why it matters

Without a table name these commands process every table (or index) they can reach, so the time the migration takes depends on the size of the whole database, which differs between environments and grows over time. `VACUUM` and the wide `REINDEX` forms also cannot run inside a transaction block, and the non-concurrent `REINDEX` holds `SHARE` on each table in turn, blocking writes to it while its indexes are rebuilt. Autovacuum already analyses changed tables; a migration that needs fresh statistics usually needs them for one or two tables.

## Example

Flagged:

```sql
ALTER TABLE orders ADD COLUMN region text;
UPDATE orders SET region = 'eu' WHERE id < 10000;
ANALYZE;
```

Preferred:

```sql
ALTER TABLE orders ADD COLUMN region text;
UPDATE orders SET region = 'eu' WHERE id < 10000;
ANALYZE orders;
```

## How ProdShadow verifies it

The candidate run reports the statement's duration on the fixture, which is smaller than production; the static finding is the main signal.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS126: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS126 reason="why this is acceptable" expires=2027-06-30
```
