# PS128 · enum-value-used-before-commit

| Default severity | Evidence |
|---|---|
| critical | static |

## What it detects

A statement that uses an enum value (as a quoted literal) which an earlier `ALTER TYPE ... ADD VALUE` of the same transaction added. Transactions follow `migration.transaction`, the same plan the experiment executes.

## Why it matters

Since PostgreSQL 12, `ALTER TYPE ... ADD VALUE` may run inside a transaction block, but the new value cannot be used until that transaction commits; PostgreSQL rejects the use with `unsafe use of new value`. Migrations that add a value and backfill it in one file fail at deploy time. The exception is an enum type created in the same transaction, which is not flagged.

## Example

Flagged:

```sql
ALTER TYPE order_status ADD VALUE 'refunded';
UPDATE orders SET status = 'refunded'
 WHERE refunded_at IS NOT NULL;
```

Preferred:

```sql
-- 0041_add_refunded_status.sql
ALTER TYPE order_status ADD VALUE 'refunded';

-- 0042_backfill_refunded.sql (separate transaction)
UPDATE orders SET status = 'refunded'
 WHERE refunded_at IS NOT NULL;
```

## How ProdShadow verifies it

The candidate run executes the statements and reports the failure as `OBS003` with SQLSTATE `55P04`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS128: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS128 reason="why this is acceptable" expires=2027-06-30
```
