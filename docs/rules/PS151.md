# PS151 · non-immutable-check

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

A `CHECK` constraint, added by `CREATE TABLE` or `ALTER TABLE`, whose expression uses the current time (`now()`, `CURRENT_DATE`, `CURRENT_TIMESTAMP`, `clock_timestamp()`, ...), randomness, `current_setting()` or the current user.

## Why it matters

PostgreSQL assumes `CHECK` expressions are immutable: a row is checked when it is inserted or updated, never again. A constraint such as `CHECK (expires_at > now())` therefore holds for new rows but stops holding for old ones as time passes, so the constraint no longer describes the data. Restoring a dump re-checks every row and fails, and a later `VALIDATE CONSTRAINT` fails too. The PostgreSQL manual warns against exactly this.

## Example

Flagged:

```sql
ALTER TABLE tokens ADD CONSTRAINT tokens_not_expired
  CHECK (expires_at > now()) NOT VALID;
```

Preferred:

```sql
-- enforce the rule when writing, in a trigger or in the application,
-- and keep CHECK constraints immutable:
ALTER TABLE tokens ADD CONSTRAINT tokens_expiry_after_issue
  CHECK (expires_at > issued_at) NOT VALID;
```

## How ProdShadow verifies it

Static only.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS151: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS151 reason="why this is acceptable" expires=2027-06-30
```
