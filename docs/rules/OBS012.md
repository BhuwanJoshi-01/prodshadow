# OBS012 · queued-session-budget

| Default severity | Evidence |
|---|---|
| critical | observed |

## What it detects

More workload sessions were sampled queued behind the migration's lock request at the same time than `policy.max_queued_sessions` allows. The budget is optional; without it the queue is only reported by `OBS011`.

## Why it matters

Every session waiting behind the migration holds a database connection and an application request. Once the queue reaches the size of the application's connection pool, new requests cannot get a connection at all, even for tables the migration does not touch. A short lock wait that stays within `max_lock_wait_ms` can still exhaust a small pool on a busy table.

## Example

Flagged:

```yaml
policy:
  max_lock_wait_ms: 2000
```

Preferred:

```yaml
policy:
  max_lock_wait_ms: 2000
  # application pool size is 20 per instance; keep a margin
  max_queued_sessions: 10
```

## How ProdShadow verifies it

Counts come from `pg_blocking_pids()` samples every `telemetry.sample_interval_ms`, so they are a lower bound; confidence reflects how many candidate repeats exceeded the budget. The workload's `concurrency` caps how large the queue can get, so set it near production's per-table concurrency.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS012: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore OBS012 reason="why this is acceptable" expires=2027-06-30
```
