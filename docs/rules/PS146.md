# PS146 · security-definer-search-path

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`CREATE FUNCTION` or `CREATE PROCEDURE` with `SECURITY DEFINER` and no `SET search_path` option.

## Why it matters

A `SECURITY DEFINER` function runs with its owner's privileges. Unless its `search_path` is fixed, unqualified names inside it are resolved through the caller's `search_path`, so a caller who can create objects in any schema on that path can substitute their own function, operator or table and run code as the owner. The PostgreSQL manual recommends always setting `search_path` for such functions, with `pg_temp` last.

## Example

Flagged:

```sql
CREATE FUNCTION archive_order(order_id bigint) RETURNS void\nLANGUAGE sql SECURITY DEFINER AS $$\n  UPDATE orders SET archived = true WHERE id = order_id;\n$$;
```

Preferred:

```sql
CREATE FUNCTION archive_order(order_id bigint) RETURNS void\nLANGUAGE sql SECURITY DEFINER\nSET search_path = pg_catalog, pg_temp AS $$\n  UPDATE public.orders SET archived = true WHERE id = order_id;\n$$;\nREVOKE EXECUTE ON FUNCTION archive_order(bigint) FROM PUBLIC;
```

## How ProdShadow verifies it

Static only.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS146: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS146 reason="why this is acceptable" expires=2027-06-30
```
