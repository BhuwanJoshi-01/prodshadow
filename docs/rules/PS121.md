# PS121 · concurrent-index-caveats

| Default severity | Evidence |
|---|---|
| info | static |

## What it detects

`CREATE INDEX CONCURRENTLY` on a pre-existing table.

## Why it matters

The concurrent build does not block writes, but it scans the table twice, must wait for every transaction that might use the index (so a long transaction delays it), and if it fails it leaves an `INVALID` index that keeps costing write overhead until dropped.

## Example

Flagged:

```sql
CREATE INDEX CONCURRENTLY orders_status_idx ON orders (status);
```

Preferred:

```sql
CREATE INDEX CONCURRENTLY orders_status_idx ON orders (status);
-- after a failure:
-- SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
-- DROP INDEX CONCURRENTLY orders_status_idx;
```

## How ProdShadow verifies it

The candidate run reports the build's duration and confirms that no session queued behind it.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS121: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS121 reason="why this is acceptable" expires=2027-06-30
```
