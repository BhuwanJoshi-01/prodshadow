# PS158 · concurrent-refresh-unsupported

| Default severity | Evidence |
|---|---|
| critical | static |

## What it detects

`REFRESH MATERIALIZED VIEW CONCURRENTLY` on a materialized view that, according to the fixture schema and the migration so far, has no unique index on plain columns without a `WHERE` clause, or is not populated (created `WITH NO DATA` and not refreshed since). Without a fixture schema the rule is silent.

## Why it matters

A concurrent refresh matches old and new rows through such a unique index, and diffs against existing contents, so PostgreSQL rejects it on a view without one (SQLSTATE `55000`) or on an unpopulated view (`0A000`). Teams usually switch to `CONCURRENTLY` precisely because the plain refresh blocked readers ([PS113](PS113.md)); without the index the migration fails instead.

## Example

Flagged:

```sql
CREATE MATERIALIZED VIEW status_counts AS
    SELECT status, count(*) AS n FROM orders GROUP BY status;
-- later:
REFRESH MATERIALIZED VIEW CONCURRENTLY status_counts;
```

Preferred:

```sql
CREATE UNIQUE INDEX CONCURRENTLY status_counts_status ON status_counts (status);
REFRESH MATERIALIZED VIEW CONCURRENTLY status_counts;
```

## How ProdShadow verifies it

The lock oracle integration test runs both failing forms against PostgreSQL and checks the SQLSTATE; `verify` reports the failure as `OBS003`. The [matview-refresh example](../../examples/matview-refresh) shows the concurrent refresh with the index it needs.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS158: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS158 reason="why this is acceptable" expires=2027-06-30
```
