# PS154 · concurrent-index-on-partitioned-table

| Default severity | Evidence |
|---|---|
| critical | static |

## What it detects

`CREATE INDEX CONCURRENTLY` on a table that an earlier statement of the migration shows to be partitioned: created with `PARTITION BY`, or the parent in `PARTITION OF` or `ATTACH PARTITION`. Tables partitioned by earlier migrations are not visible, so those cases are only caught by the experiment.

## Why it matters

PostgreSQL does not support building an index on a partitioned table concurrently; the statement fails. Building it without `CONCURRENTLY` locks the parent and every partition against writes for the whole build. The supported way is to create the index on the parent only, which is instant and starts out invalid, build each partition's index concurrently, and attach them; the parent index becomes valid once every partition has one.

## Example

Flagged:

```sql
CREATE INDEX CONCURRENTLY events_at_idx ON events (at);
```

Preferred:

```sql
CREATE INDEX events_at_idx ON ONLY events (at);\n-- for each partition, outside a transaction block:\nCREATE INDEX CONCURRENTLY events_2026_at_idx ON events_2026 (at);\nALTER INDEX events_at_idx ATTACH PARTITION events_2026_at_idx;
```

## How ProdShadow verifies it

The candidate run executes the statement and reports the failure as `OBS003`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS154: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS154 reason="why this is acceptable" expires=2027-06-30
```
