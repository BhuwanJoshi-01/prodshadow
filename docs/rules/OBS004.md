# OBS004 · migration-statement-timeout

| Default severity | Evidence |
|---|---|
| critical | observed |

## What it detects

A migration statement was cancelled by `migration.statement_timeout_ms` (SQLSTATE `57014`).

## Why it matters

If a statement cannot finish within the budget on a small fixture, it will take far longer in production, usually while holding a blocking lock.

## Example

Flagged:

```sql
UPDATE subscribers SET email_normalized = lower(email);
```

Preferred:

```sql
UPDATE subscribers SET email_normalized = lower(email)
WHERE id BETWEEN $1 AND $2;  -- batched, outside the schema migration
```

## How ProdShadow verifies it

Raise `migration.statement_timeout_ms` only if the operation is genuinely expected to be long and non-blocking.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS004: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore OBS004 reason="why this is acceptable" expires=2027-06-30
```
