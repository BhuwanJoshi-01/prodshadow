# PS131 · server-file-access

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`COPY ... FROM` or `COPY ... TO` a file name or `PROGRAM`, and calls to `pg_read_file`, `pg_read_binary_file`, `pg_stat_file`, `pg_ls_dir`, `lo_import` or `lo_export`.

## Why it matters

These run on the database server, not on the machine that runs the migration: a `COPY` file path names a file on the server, and `PROGRAM` runs a shell command as the server's operating system user. They need superuser or the `pg_read_server_files`, `pg_write_server_files` or `pg_execute_server_program` roles, which managed services do not grant and a migration role should not hold. The files also differ between development, CI and production, so the migration behaves differently in each.

## Example

Flagged:

```sql
COPY countries FROM '/data/countries.csv' WITH (FORMAT csv);
```

Preferred:

```sql
-- in the deploy job, from the client side:
-- psql -c "\copy countries FROM 'data/countries.csv' WITH (FORMAT csv)"
-- or ship the rows in the migration:
INSERT INTO countries (code, name) VALUES ('NP', 'Nepal'), ('PT', 'Portugal');
```

## How ProdShadow verifies it

The disposable server has no network and none of your files, so the statement fails in the candidate run and is reported as `OBS003`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS131: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS131 reason="why this is acceptable" expires=2027-06-30
```
