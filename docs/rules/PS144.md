# PS144 · row-security-disabled

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`ALTER TABLE ... DISABLE ROW LEVEL SECURITY`, `ALTER TABLE ... NO FORCE ROW LEVEL SECURITY` and `DROP POLICY`.

## Why it matters

Row-level security policies are often the only thing separating tenants or users in a shared table. Disabling row-level security turns every policy on the table off at once, so any role with table privileges sees and changes every row; `NO FORCE` exempts the table owner again; dropping a policy removes one rule, which exposes rows unless another policy covers them. These changes take effect for every session immediately, including the running application. `DROP POLICY` is reported as a heuristic because a replacement policy may exist.

## Example

Flagged:

```sql
ALTER TABLE accounts DISABLE ROW LEVEL SECURITY;\nUPDATE accounts SET plan = 'basic' WHERE plan IS NULL;
```

Preferred:

```sql
BEGIN;\nCREATE POLICY tenant_isolation_v2 ON accounts\n  USING (tenant_id = current_setting('app.tenant_id')::bigint);\nDROP POLICY tenant_isolation ON accounts;\nCOMMIT;
```

## How ProdShadow verifies it

Static only: workload sessions connect as the table owner, which policies do not restrict unless `FORCE ROW LEVEL SECURITY` is set.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS144: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS144 reason="why this is acceptable" expires=2027-06-30
```
