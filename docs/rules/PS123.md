# PS123 · attach-partition-scans

| Default severity | Evidence |
|---|---|
| warning | heuristic |

## What it detects

`ALTER TABLE ... ATTACH PARTITION` of a table that existed before the migration, unless an earlier statement of the migration adds a `CHECK` constraint to it.

## Why it matters

To attach a partition, PostgreSQL verifies that every row satisfies the partition bounds, scanning the whole partition while it holds `ACCESS EXCLUSIVE` on it (the parent only gets `SHARE UPDATE EXCLUSIVE`). If a valid `CHECK` constraint already implies the bounds, the scan is skipped. ProdShadow cannot see constraints created by earlier migrations, so the finding is a heuristic.

## Example

Flagged:

```sql
ALTER TABLE events ATTACH PARTITION events_2026
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
```

Preferred:

```sql
ALTER TABLE events_2026 ADD CONSTRAINT events_2026_bounds
  CHECK (at >= '2026-01-01' AND at < '2027-01-01') NOT VALID;
ALTER TABLE events_2026 VALIDATE CONSTRAINT events_2026_bounds;
ALTER TABLE events ATTACH PARTITION events_2026
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
ALTER TABLE events_2026 DROP CONSTRAINT events_2026_bounds;
```

## How ProdShadow verifies it

The candidate run measures how long the partition was locked on your fixture.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS123: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS123 reason="why this is acceptable" expires=2027-06-30
```
