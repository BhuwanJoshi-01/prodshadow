# PS114 · missing-lock-timeout

| Default severity | Evidence |
|---|---|
| info | static |

## What it detects

The first statement that requests a lock blocking reads or writes on a pre-existing table, when no `SET lock_timeout` precedes it in the migration.

## Why it matters

If any transaction holds a conflicting lock, the request waits — by default forever — and PostgreSQL queues every later request on the table behind it. A short `lock_timeout` turns a potential outage into a failed migration that can be retried. ProdShadow always applies `migration.lock_timeout_ms` during the rehearsal; this finding reminds you that production runs need the same protection.

## Example

Flagged:

```sql
ALTER TABLE orders ADD COLUMN note text;
```

Preferred:

```sql
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN note text;
-- and retry the migration with backoff on SQLSTATE 55P03
```

## How ProdShadow verifies it

Add a background session that holds a transaction open. The candidate run then reproduces the lock queue and reports `OBS002`. See [examples/long-running-transaction](../../examples/long-running-transaction).

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS114: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS114 reason="why this is acceptable" expires=2027-06-30
```
