# PS138 · privileges-revoked

| Default severity | Evidence |
|---|---|
| warning | heuristic |

## What it detects

`REVOKE` (on tables, sequences, functions, schemas or all objects in a schema), `ALTER DEFAULT PRIVILEGES ... REVOKE`, `DROP OWNED BY` and `DROP ROLE`.

## Why it matters

Privilege changes take effect immediately for every session, including the connections of the application version that is currently deployed, so a `REVOKE` meant for a later release breaks the running one with `permission denied` (SQLSTATE `42501`). `ALTER DEFAULT PRIVILEGES ... REVOKE` fails later and more confusingly, when the next table is created. `DROP OWNED BY` also drops the role's objects, and `DROP ROLE` affects the whole cluster. The migration does not show which roles the application uses, so the finding is a heuristic.

## Example

Flagged:

```sql
REVOKE SELECT ON customers FROM reporting;
```

Preferred:

```sql
-- release N: switch the reporting job to the reporting_v2 role\n-- release N+1, once no session logs in as reporting:\nREVOKE SELECT ON customers FROM reporting;
```

## How ProdShadow verifies it

Workload sessions connect as the fixture owner, so revoking from other roles does not show up in the candidate run; compatibility probes run as the same role.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS138: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS138 reason="why this is acceptable" expires=2027-06-30
```
