# PS115 · lock-held-across-statements

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

A statement that takes a blocking lock inside a transaction (explicit `BEGIN`, or a file wrapped by `migration.transaction`) that runs further statements afterwards.

## Why it matters

Locks are released at `COMMIT`, not when the statement ends. A quick `ALTER TABLE` followed by a backfill in the same transaction keeps `ACCESS EXCLUSIVE` for the duration of the backfill.

## Example

Flagged:

```sql
ALTER TABLE orders ADD COLUMN note text;
UPDATE orders SET note = '' WHERE note IS NULL;  -- same transaction
```

Preferred:

```sql
-- file 1
ALTER TABLE orders ADD COLUMN note text;
-- file 2 (or a batched script)
UPDATE orders SET note = '' WHERE id BETWEEN $1 AND $2;
```

## How ProdShadow verifies it

The finding uses the same transaction plan as the executor. The candidate run measures how long the lock was held in total.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS115: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS115 reason="why this is acceptable" expires=2027-06-30
```
