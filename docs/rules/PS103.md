# PS103 · add-column-rewrites-table

| Default severity | Evidence |
|---|---|
| warning | static (heuristic for unknown functions) |

## What it detects

`ALTER TABLE ... ADD COLUMN` whose new column forces PostgreSQL to rewrite every row: a default that calls a volatile function (`gen_random_uuid()`, `random()`, `clock_timestamp()`, `nextval()`, ...), a `serial`/`bigserial` type, an identity column, or a stored generated column.

## Why it matters

Since PostgreSQL 11, adding a column with a constant or stable default is a catalog-only change. A volatile default must be evaluated for each existing row, so the whole table is rewritten while `ACCESS EXCLUSIVE` is held: reads and writes wait for the full rewrite. Defaults calling functions ProdShadow does not know are reported with low confidence.

## Example

Flagged:

```sql
ALTER TABLE orders ADD COLUMN public_id uuid DEFAULT gen_random_uuid();
```

Preferred:

```sql
ALTER TABLE orders ADD COLUMN public_id uuid;
ALTER TABLE orders ALTER COLUMN public_id SET DEFAULT gen_random_uuid();
-- backfill existing rows in batches, outside the schema migration
```

## How ProdShadow verifies it

The candidate run measures how long the rewrite holds the lock on your fixture and what the workload experienced meanwhile. Durations scale with table size.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS103: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS103 reason="why this is acceptable" expires=2027-06-30
```
