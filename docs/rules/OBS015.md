# OBS015 · extra-wal-budget

| Default severity | Evidence |
|---|---|
| critical | observed |

## What it detects

The median, across repeats, of how much more write-ahead log a candidate phase wrote than its paired baseline exceeds `policy.max_extra_wal_mb`. The budget is optional; without it the rule does not run. WAL is measured with `pg_current_wal_lsn()` before and after each phase.

## Why it matters

Every change PostgreSQL makes goes through the WAL, which streaming replicas, WAL archiving, backups and logical decoding must all receive and apply. A table rewrite or a large backfill writes the whole table again in a short time, so replicas fall behind (and reads from them go stale), archives grow, and in the worst case a replication slot holds back WAL until the disk fills. The fixture is smaller than production, so treat the measured volume as a lower bound that scales with the table size.

## Example

Flagged:

```yaml
policy:
  max_lock_wait_ms: 2000
```

Preferred:

```yaml
policy:
  max_lock_wait_ms: 2000
  # this fixture's orders table is about 40 MiB
  max_extra_wal_mb: 20
```

## How ProdShadow verifies it

Each phase records `wal_bytes` in `phases[].counters`; the finding compares each candidate with the baseline of the same repeat, so workload WAL cancels out. Confidence reflects how many repeats exceeded the budget.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS015: critical   # or info, warning, off
```

Suppress a reviewed case in the suppressions file (`policy.suppressions`):

```yaml
version: 1
suppressions:
  - rule: OBS015
    reason: "why this is acceptable"
    expires: 2027-06-30
```
