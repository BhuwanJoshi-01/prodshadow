# PS141 · create-partition-locks-parent

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`CREATE TABLE ... PARTITION OF` a partitioned table that existed before the migration.

## Why it matters

Creating a partition with `PARTITION OF` takes `ACCESS EXCLUSIVE` on the partitioned table, blocking every query on all of its partitions until the transaction commits, and queueing them while it waits. Creating the table separately and attaching it needs only `SHARE UPDATE EXCLUSIVE` on the parent; with a `CHECK` constraint that matches the bounds the attach also skips its validation scan (see [PS123](PS123.md)). This matters most for jobs that create next month's partition while the table is busy.

## Example

Flagged:

```sql
CREATE TABLE events_2027 PARTITION OF events\n  FOR VALUES FROM ('2027-01-01') TO ('2028-01-01');
```

Preferred:

```sql
CREATE TABLE events_2027 (LIKE events INCLUDING ALL);\nALTER TABLE events_2027 ADD CONSTRAINT events_2027_bounds\n  CHECK (at >= '2027-01-01' AND at < '2028-01-01');\nALTER TABLE events ATTACH PARTITION events_2027\n  FOR VALUES FROM ('2027-01-01') TO ('2028-01-01');\nALTER TABLE events_2027 DROP CONSTRAINT events_2027_bounds;
```

## How ProdShadow verifies it

The candidate run shows workload sessions queued behind the `CREATE TABLE`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS141: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS141 reason="why this is acceptable" expires=2027-06-30
```
