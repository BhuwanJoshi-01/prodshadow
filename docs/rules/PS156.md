# PS156 · sequence-change-blocks-inserts

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`ALTER SEQUENCE` on a sequence that existed before the migration, in any form (`RESTART`, `INCREMENT BY`, `CACHE`, `OWNED BY`, ...). With the fixture schema, the finding names the columns that draw from the sequence by default (serial and identity columns, `DEFAULT nextval(...)`).

## Why it matters

Every `ALTER SEQUENCE` takes `SHARE ROW EXCLUSIVE` on the sequence. Calling `nextval()` takes `ROW EXCLUSIVE` on it, and like every relation lock it is held until the transaction ends, so the change waits for all in-flight transactions that inserted a row using the sequence, and while it waits, every new insert queues behind it. On a busy table this is a short stall at best and an outage behind one long transaction at worst.

## Example

Flagged:

```sql
ALTER SEQUENCE orders_id_seq CACHE 50;
```

Preferred:

```sql
SET lock_timeout = '2s';
ALTER SEQUENCE orders_id_seq CACHE 50;
-- retried by the deploy tool on lock_timeout (migration.lock_retries)
```

## How ProdShadow verifies it

`verify` measures the wait: with insert scenarios on the table, a queued `ALTER SEQUENCE` shows as `OBS001`/`OBS002`. The lock oracle integration test checks the lock modes on every supported PostgreSQL version.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS156: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS156 reason="why this is acceptable" expires=2027-06-30
```
