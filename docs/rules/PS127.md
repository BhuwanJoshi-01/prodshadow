# PS127 · extension-requires-preload

| Default severity | Evidence |
|---|---|
| warning | heuristic |

## What it detects

`CREATE EXTENSION` of a well-known extension whose library must be listed in `shared_preload_libraries`: `citus`, `pg_cron`, `pg_squeeze`, `pglogical`, `timescaledb`, `pg_stat_statements`, `pg_stat_kcache`, `pg_wait_sampling`, `pg_qualstats` and `pgaudit`.

## Why it matters

`shared_preload_libraries` only changes on a server restart, so it cannot be fixed by the migration itself. Where the library is not preloaded, `CREATE EXTENSION` fails for some of these extensions; for others it succeeds and the extension then raises errors or silently does nothing. Local and CI databases are often started with the library preloaded when a production server, or a managed service's parameter group, is not. ProdShadow cannot see the target server's settings, so the finding is a heuristic.

## Example

Flagged:

```sql
CREATE EXTENSION pg_cron;
```

Preferred:

```sql
-- shared_preload_libraries includes pg_cron on every target server
-- (checked in the deploy runbook), then:
CREATE EXTENSION pg_cron;
```

## How ProdShadow verifies it

The candidate run uses the configured PostgreSQL image. If that image does not preload the library, the statement fails there too; if it does, the run cannot tell whether production does.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS127: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS127 reason="why this is acceptable" expires=2027-06-30
```
