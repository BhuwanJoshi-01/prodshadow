# PS134 · unbalanced-transaction-control

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

Within one migration file: a `BEGIN` (or `START TRANSACTION`) that is never followed by `COMMIT` or `ROLLBACK`, a `BEGIN` inside a transaction that is already open, and a `COMMIT` or `ROLLBACK` with no `BEGIN` before it.

## Why it matters

PostgreSQL does not fail on any of these. A nested `BEGIN` and a `COMMIT` outside a transaction only produce a warning, and a transaction that is still open when the session ends is silently rolled back, so a missing `COMMIT` can discard the whole migration while the tool reports success. A stray `COMMIT` means the statements before it did not run in a transaction at all, or, when the migration tool wraps the file in its own transaction, that it ended the tool's transaction early. Files are checked separately because migration tools usually run each in its own transaction.

## Example

Flagged:

```sql
BEGIN;
ALTER TABLE orders ADD COLUMN region text;
UPDATE orders SET region = 'eu' WHERE id < 10000;
```

Preferred:

```sql
BEGIN;
ALTER TABLE orders ADD COLUMN region text;
UPDATE orders SET region = 'eu' WHERE id < 10000;
COMMIT;
```

## How ProdShadow verifies it

The candidate run executes the files on one session as written, so an unterminated transaction is rolled back when the migration session closes.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS134: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS134 reason="why this is acceptable" expires=2027-06-30
```
