# OBS016 · temp-file-spill

| Default severity | Evidence |
|---|---|
| info | observed |

## What it detects

Candidate phases wrote more than 1 MiB of temporary files beyond their paired baselines (median across repeats), measured with `pg_stat_database.temp_bytes`.

## Why it matters

When a sort or an index build does not fit in `work_mem` or `maintenance_work_mem`, PostgreSQL spills to temporary files. The operation becomes slower and I/O-bound, and holds its locks longer; `CREATE INDEX` without `CONCURRENTLY` keeps writes blocked for the whole build. The fixture is smaller than production, so a spill seen here is larger in production, and a build that fits in memory here may not fit there.

## Example

Flagged:

```sql
CREATE INDEX CONCURRENTLY orders_created_idx ON orders (created_at);
```

Preferred:

```sql
SET maintenance_work_mem = '1GB';
CREATE INDEX CONCURRENTLY orders_created_idx ON orders (created_at);
```

## How ProdShadow verifies it

Each phase records `temp_bytes` in `phases[].counters`; each candidate is compared with the baseline of the same repeat, so temporary files written by the workload cancel out.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS016: critical   # or info, warning, off
```

Suppress a reviewed case in the suppressions file (`policy.suppressions`):

```yaml
version: 1
suppressions:
  - rule: OBS016
    reason: "why this is acceptable"
    expires: 2027-06-30
```
