# PS132 · unnamed-concurrent-index

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`CREATE INDEX CONCURRENTLY` without an index name, on a table that existed before the migration.

## Why it matters

A concurrent index build that fails, for example on a lock timeout, a deadlock or a duplicate value for a unique index, leaves an `INVALID` index behind. With a generated name, running the migration again does not fail on the existing name: PostgreSQL picks the next free name (`orders_customer_id_idx1`) and builds a second index. Invalid indexes are not used by queries but are still updated on every write, so each retry makes writes slower. A named index also allows `DROP INDEX CONCURRENTLY IF EXISTS` before the retry.

## Example

Flagged:

```sql
CREATE INDEX CONCURRENTLY ON orders (customer_id);
```

Preferred:

```sql
DROP INDEX CONCURRENTLY IF EXISTS orders_customer_id_idx;
CREATE INDEX CONCURRENTLY orders_customer_id_idx ON orders (customer_id);
```

## How ProdShadow verifies it

Static only. Find leftovers in production with `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS132: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS132 reason="why this is acceptable" expires=2027-06-30
```
