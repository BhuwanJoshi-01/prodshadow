# PS102 · concurrent-operation-in-transaction

| Default severity | Evidence |
|---|---|
| critical | static |

## What it detects

A statement that cannot run inside a transaction block — `CREATE INDEX CONCURRENTLY`, `DROP INDEX CONCURRENTLY`, `REINDEX ... CONCURRENTLY`, `VACUUM`, `ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY` — that follows an explicit `BEGIN`, or that `migration.transaction: per-file` would wrap.

## Why it matters

PostgreSQL rejects these statements inside a transaction block with `ERROR: ... cannot run inside a transaction block`. The migration fails in production exactly as it does here.

## Example

Flagged:

```sql
BEGIN;
CREATE INDEX CONCURRENTLY orders_status_idx ON orders (status);
COMMIT;
```

Preferred:

```sql
-- no BEGIN/COMMIT around it; keep it in its own file
CREATE INDEX CONCURRENTLY orders_status_idx ON orders (status);
```

## How ProdShadow verifies it

With `migration.transaction: auto`, ProdShadow never wraps such a file itself. The candidate run reports the actual failure as `OBS003` with SQLSTATE `25001`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS102: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS102 reason="why this is acceptable" expires=2027-06-30
```
