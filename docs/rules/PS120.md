# PS120 · ineffective-lock-timeout

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`SET lock_timeout = 0` (which disables the timeout) or a value above 10 seconds.

## Why it matters

While a migration waits for its lock, every later query on the table waits behind it. A long `lock_timeout` lets that queue build for its whole length; `0` lets it build forever.

## Example

Flagged:

```sql
SET lock_timeout = '1min';
ALTER TABLE orders ADD COLUMN note text;
```

Preferred:

```sql
SET lock_timeout = '2s';
ALTER TABLE orders ADD COLUMN note text;
-- retry on SQLSTATE 55P03
```

## How ProdShadow verifies it

The candidate run uses the timeout the migration sets, so a long timeout shows up as long workload stalls (`OBS001`).

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS120: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS120 reason="why this is acceptable" expires=2027-06-30
```
