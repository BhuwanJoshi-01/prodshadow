# PS107 · constraint-validated-in-place

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`ADD CONSTRAINT ... FOREIGN KEY` or `ADD CONSTRAINT ... CHECK` without `NOT VALID`, and `ADD COLUMN ... REFERENCES ...` or `ADD COLUMN ... CHECK (...)` (inline constraints, which cannot be `NOT VALID`).

## Why it matters

Validation reads every existing row while the lock is held. A foreign key takes `SHARE ROW EXCLUSIVE` on both tables, blocking writes to both for the whole validation; a `CHECK` constraint takes `ACCESS EXCLUSIVE`. Adding the constraint `NOT VALID` and validating it separately needs only `SHARE UPDATE EXCLUSIVE`, which does not block reads or writes.

## Example

Flagged:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_customer_fk
  FOREIGN KEY (customer_id) REFERENCES customers (id);
```

Preferred:

```sql
ALTER TABLE orders ADD CONSTRAINT orders_customer_fk
  FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID;
-- separate transaction
ALTER TABLE orders VALIDATE CONSTRAINT orders_customer_fk;
```

## How ProdShadow verifies it

Write scenarios on both tables stall for the duration of the validation; `OBS001` and `OBS011` report it.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS107: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS107 reason="why this is acceptable" expires=2027-06-30
```
