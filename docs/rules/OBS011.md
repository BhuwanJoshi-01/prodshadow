# OBS011 · sessions-queued-behind-migration

| Default severity | Evidence |
|---|---|
| info | observed |

## What it detects

Workload sessions were sampled waiting with the migration's process listed by `pg_blocking_pids()` — they queued behind its lock request — together with the relation, the lock mode and the sessions the migration itself waited for.

## Why it matters

This is the evidence that explains `OBS001` and `OBS002`: who blocked whom. It is reported even when the wait stayed within budget, because a queue that formed on a small fixture forms in production too.

## Example

Flagged:

```sql
-- ALTER TABLE issued while a long transaction is open
```

Preferred:

```sql
SET lock_timeout = '2s';
```

## How ProdShadow verifies it

Sampling runs every `telemetry.sample_interval_ms`; very short queues can be missed, and the server log covers waits longer than `deadlock_timeout`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS011: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore OBS011 reason="why this is acceptable" expires=2027-06-30
```
