# PS124 · cascade-drop

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`DROP ... CASCADE`, `TRUNCATE ... CASCADE` and `ALTER TABLE ... DROP COLUMN | DROP CONSTRAINT ... CASCADE` on objects that existed before the migration.

## Why it matters

With `CASCADE`, PostgreSQL removes every object that depends on the target: views, foreign keys of other tables, column defaults that call a dropped function, and so on. `TRUNCATE ... CASCADE` empties every table that references the target through a foreign key, and the tables referencing those. The set of objects is decided by the production schema at the time the migration runs, not by the migration text, so a reviewer cannot see what will be removed. Without `CASCADE` (`RESTRICT` is the default), an unexpected dependency makes the statement fail instead.

## Example

Flagged:

```sql
DROP TABLE legacy_accounts CASCADE;
```

Preferred:

```sql
DROP VIEW account_summary;
ALTER TABLE invoices DROP CONSTRAINT invoices_account_fk;
DROP TABLE legacy_accounts;
```

## How ProdShadow verifies it

Static only. The candidate run executes the cascade against your fixture schema, so a later statement or workload query that uses a removed object fails there, but objects only present in production are not covered.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS124: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS124 reason="why this is acceptable" expires=2027-06-30
```
