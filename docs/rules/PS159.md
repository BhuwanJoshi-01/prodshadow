# PS159 · dependent-view

| Default severity | Evidence |
|---|---|
| critical | static |

## What it detects

`ALTER TABLE ... DROP COLUMN` (without `CASCADE`) or `ALTER COLUMN ... TYPE` on a column that a view or materialized view reads, or `DROP TABLE` (without `CASCADE`) on a table a view reads, according to the fixture schema and the migration so far. Views dropped earlier in the migration no longer count. `SELECT *` views depend on every column the table had when the view was created. Without a fixture schema the rule is silent.

## Why it matters

PostgreSQL keeps views consistent with their tables: it refuses to drop a column or table a view depends on (SQLSTATE `2BP01`) and cannot change the type of a column a view uses (`0A000`). The migration fails at that statement; in a file that is not one transaction, earlier statements stay applied. With `CASCADE` the drop succeeds and silently removes the views, and the application then fails on them instead ([PS124](PS124.md)).

## Example

Flagged:

```sql
-- recent_orders is a view that selects orders.status
ALTER TABLE orders DROP COLUMN status;
```

Preferred:

```sql
BEGIN;
DROP VIEW recent_orders;
ALTER TABLE orders DROP COLUMN status;
CREATE VIEW recent_orders AS SELECT id, created_at FROM orders;
COMMIT;
```

## How ProdShadow verifies it

The failure oracle integration test runs the three failing forms against PostgreSQL and checks the SQLSTATE; `verify` reports the failure as `OBS003`.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS159: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS159 reason="why this is acceptable" expires=2027-06-30
```
