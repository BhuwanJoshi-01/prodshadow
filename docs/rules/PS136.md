# PS136 · validated-in-same-transaction

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`ALTER TABLE ... VALIDATE CONSTRAINT` in the same transaction as the `ADD CONSTRAINT ... NOT VALID` that created the constraint. Transactions follow `migration.transaction`, the same plan the experiment executes.

## Why it matters

Adding a foreign key or `CHECK` constraint `NOT VALID` takes a strong lock (`SHARE ROW EXCLUSIVE` or `ACCESS EXCLUSIVE`) only briefly, and `VALIDATE CONSTRAINT` then scans the table under `SHARE UPDATE EXCLUSIVE`, which does not block reads or writes. That split only helps if the two run in separate transactions: locks are held until `COMMIT`, so in one transaction the validation scan runs while the strong lock from the `ADD` is still held, and writes (or all traffic) wait for the whole scan.

## Example

Flagged:

```sql
ALTER TABLE refunds ADD CONSTRAINT refunds_order_fk
  FOREIGN KEY (order_id) REFERENCES orders (id) NOT VALID;
ALTER TABLE refunds VALIDATE CONSTRAINT refunds_order_fk;
-- both in one migration file, wrapped in one transaction
```

Preferred:

```sql
-- 0051_add_refunds_order_fk.sql
ALTER TABLE refunds ADD CONSTRAINT refunds_order_fk
  FOREIGN KEY (order_id) REFERENCES orders (id) NOT VALID;

-- 0052_validate_refunds_order_fk.sql
ALTER TABLE refunds VALIDATE CONSTRAINT refunds_order_fk;
```

## How ProdShadow verifies it

The candidate run shows the lock held across the scan as waiting workload sessions; `PS115` reports the same lock being held across statements in general.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS136: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS136 reason="why this is acceptable" expires=2027-06-30
```
