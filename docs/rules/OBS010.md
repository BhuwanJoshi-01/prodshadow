# OBS010 · deadlocks

| Default severity | Evidence |
|---|---|
| warning | observed |

## What it detects

`pg_stat_database.deadlocks` increased during a candidate phase.

## Why it matters

A migration that locks several tables in a different order than the application does can deadlock with it. PostgreSQL resolves deadlocks by aborting one transaction — possibly the migration, possibly a user request.

## Example

Flagged:

```sql
BEGIN;
LOCK TABLE customers;
LOCK TABLE orders;  -- the application locks orders first
COMMIT;
```

Preferred:

```sql
-- take locks in the same order as the application, or one table per transaction
```

## How ProdShadow verifies it

The count comes from the server, so short-lived deadlocks are never missed.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS010: critical   # or info, warning, off
```

Suppress a reviewed case in the suppressions file (`policy.suppressions`):

```yaml
version: 1
suppressions:
  - rule: OBS010
    reason: "why this is acceptable"
    expires: 2027-06-30
```
