# OBS014 · migration-lock-retried

| Default severity | Evidence |
|---|---|
| info | observed |

## What it detects

With `migration.lock_retries` set, the migration failed with `lock_not_available` (SQLSTATE `55P03`) at least once and succeeded on a later attempt. The finding reports the most retries any candidate repeat needed. If every attempt fails, the run reports `OBS002` instead, with the number of retries.

## Why it matters

A short `lock_timeout` plus retries is the recommended way to run blocking DDL: an attempt that cannot get its lock gives up quickly instead of queueing everyone behind it indefinitely. But every failed attempt still makes the sessions that arrived meanwhile wait for up to the lock timeout, so a migration that needs several attempts causes several short stalls. Retries also show that something held a conflicting lock when the migration started, which may be avoidable by scheduling.

## Example

Flagged:

```sql
migration:
  lock_timeout_ms: 10000
  lock_retries: 5
```

Preferred:

```sql
migration:
  lock_timeout_ms: 1000   # each attempt stalls traffic for at most 1 s
  lock_retries: 5
  retry_backoff_ms: 2000
```

## How ProdShadow verifies it

Retries are recorded per candidate repeat in the report (`phases[].migration.retries`) with the statement, attempt number and how long each attempt waited. `OBS001` and `OBS011` show what the waiting did to the workload.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS014: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore OBS014 reason="why this is acceptable" expires=2027-06-30
```
