# OBS007 · error-rate-increase

| Default severity | Evidence |
|---|---|
| critical | observed |

## What it detects

A scenario's error rate in the candidate phases exceeds the baseline's by more than `policy.max_error_rate_increase_pct_points` (default 1 percentage point). Errors include lock and statement timeouts in workload sessions, deadlocks, undefined objects and connection failures.

## Why it matters

Errors are what users see. A migration that drops or renames something an older application version still uses produces exactly this.

## Example

Flagged:

```sql
ALTER TABLE products DROP COLUMN legacy_sku;  -- previous release still selects it
```

Preferred:

```sql
-- stop using legacy_sku in a release that is fully deployed, then drop it
```

## How ProdShadow verifies it

Declare the previous release's queries as scenarios. See [examples/rolling-deploy](../../examples/rolling-deploy).

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    OBS007: critical   # or info, warning, off
```

Suppress a reviewed case in the suppressions file (`policy.suppressions`):

```yaml
version: 1
suppressions:
  - rule: OBS007
    reason: "why this is acceptable"
    expires: 2027-06-30
```
