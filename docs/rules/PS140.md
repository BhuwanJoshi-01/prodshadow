# PS140 · detach-partition-blocks-parent

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`ALTER TABLE ... DETACH PARTITION` without `CONCURRENTLY` on a partitioned table that existed before the migration.

## Why it matters

A plain detach takes `ACCESS EXCLUSIVE` on the partitioned table, not only on the partition, so reads and writes of every partition wait for it, and queue behind it while it waits for older transactions. Since PostgreSQL 14, `DETACH PARTITION ... CONCURRENTLY` takes `SHARE UPDATE EXCLUSIVE` on the parent instead and waits for running queries in two steps. It cannot run in a transaction block, and an interrupted concurrent detach is completed with `DETACH PARTITION ... FINALIZE`.

## Example

Flagged:

```sql
ALTER TABLE events DETACH PARTITION events_2024;
```

Preferred:

```sql
-- outside a transaction block\nALTER TABLE events DETACH PARTITION events_2024 CONCURRENTLY;
```

## How ProdShadow verifies it

The candidate run shows workload sessions on other partitions queued behind the detach.

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS140: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS140 reason="why this is acceptable" expires=2027-06-30
```
