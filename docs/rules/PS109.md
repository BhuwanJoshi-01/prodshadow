# PS109 · destructive-change

| Default severity | Evidence |
|---|---|
| warning | static |

## What it detects

`DROP TABLE`, `TRUNCATE` and `ALTER TABLE ... DROP COLUMN`, and dropping a view, materialized view, sequence, function, procedure, type, domain or schema, on objects that existed before the migration. Dropping an index is left to [PS122](PS122.md), because no data is lost.

## Why it matters

The data is gone, and any application version that still reads or writes the object fails. For views, functions and types no data is lost, but the definition is, and code that calls a dropped function or queries a dropped view fails the same way. During a rolling deploy the previous version keeps serving traffic while the migration runs. The rule asks for an explicit review rather than claiming the change is wrong.

## Example

Flagged:

```sql
ALTER TABLE products DROP COLUMN legacy_sku;
```

Preferred:

```sql
-- release N:   stop reading and writing legacy_sku
-- release N+1: once no instance of release N runs
ALTER TABLE products DROP COLUMN legacy_sku;
```

## How ProdShadow verifies it

Declare the previous release's queries as workload scenarios. The candidate run then reports their failures as `OBS007`. See [examples/rolling-deploy](../../examples/rolling-deploy).

## Configuration

Change the severity or turn the rule off in `prodshadow.yaml`:

```yaml
policy:
  rules:
    PS109: critical   # or info, warning, off
```

Suppress a reviewed case next to the statement:

```sql
-- prodshadow:ignore PS109 reason="why this is acceptable" expires=2027-06-30
```
